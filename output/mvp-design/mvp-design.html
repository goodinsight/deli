01. 결론과 설계 전제

권고안은 12개 서비스의 진입점을 유지하면서, 고객·거래처·계약·일정·파일의 원본과 처리 규칙을 통합하는 것이다. 프런트엔드 메뉴 개수와 백엔드 서비스 개수를 일치시킬 필요는 없다.

구현 방식은 모듈형 모놀리스다. 하나의 업무 API와 하나의 관계형 데이터베이스를 쓰되 도메인별 소유권을 분리하고, 메일 동기화·PDF·알림·파일 검사는 별도 작업 프로세스가 처리한다.

사용자가 선택한 범위는 “12개 서비스의 핵심 흐름 구현”이다. 화면을 그대로 복제하는 프로젝트나 기존 시스템 소스 분석이 아니다. 실제 앱 구축·배포는 이번 산출물에 포함되지 않는다.

근거는 이전에 수집한 138개 화면과 화면의 문구·입력 항목이다. 원본 코드, DB 스키마, 실제 사용 로그, 인터뷰는 확보하지 않았다. 따라서 “관찰”과 “예상 불편”을 구분하며, 실제 중복 저장이나 권한 결함이 존재한다고 단정하지 않는다.

설계 가정: 국내 안전진단·시설관리 조직을 첫 고객으로 하는 웹 중심 B2B 서비스, 파일럿 1~3개 조직·조직당 50~200명·동시 활성 100명. 이 규모는 현재 서비스의 실측치가 아니며 용량 계획을 위한 가정이다.

02. 중복을 줄이는 기준

통합 대상은 작성 엔진·원본 데이터·권한·상태 규칙이다. 고객과 거래처, 업무와 달력을 모두 한 화면으로 합치는 것이 목표는 아니다. 사용자 역할에 맞는 메뉴와 뷰는 유지한다.

03. 우선순위 산정 방식

P0는 원본 데이터·금액·권한·승인의 일관성을 지키기 위해 첫 출시 전에 확정·검증할 사항이다. “현재 서비스의 심각한 버그가 확인됨”이라는 뜻이 아니다. P1은 12개 핵심 흐름을 끝까지 사용하기 위한 개선, P2는 핵심 흐름 검증 후 최적화다.

순서는 데이터 손실/불일치의 영향, 다른 기능의 선행 의존성, 적용 범위, 구현 복잡도로 판단했다. 사용 빈도·전환율·시간 절감은 실측하지 않아 RICE 같은 숫자 점수로 포장하지 않았다.

메뉴 아래 화면 유형은 목록, 상세, 작성, 승인, 보고서, 설정으로 통일한다. 업무와 고객에 같은 제목의 “새로 만들기”를 쓰기보다 “업무 등록”, “고객 추가”, “견적 작성”처럼 결과를 명시한다.

06. 핵심 흐름 A: 고객부터 수금까지

현재 메뉴를 오가더라도 하나의 거래 이야기가 이어지도록 설계한다. 상담의 “업무로 등록”이라는 기존 연결을 확장해 견적·계약·업무·수금이 서로의 원본 ID를 가진다.

1. Party와 시설물을 선택해 상담을 기록한다. 새 상대방이면 중복 후보를 보여 주고 사용자가 확인한다. 2. 상담에서 견적을 작성하면 담당자·주소·시설물을 채운다. 3. 견적의 확정 버전으로 계약을 생성한다. 계약 체결과 내부 결재 완료는 별도 상태다.

4. 계약의 실행 계획에서 프로젝트/업무를 생성한다. 5. 계약의 청구 일정으로 채권을 생성한다. 6. 통장 내역 또는 수기 입금을 기존 채권에 충당한다. 7. 계약 상세에서 업무 완료·청구·수금·잔액을 함께 본다.

개선 목표: 같은 상대방과 계약 금액을 다음 단계에서 다시 입력하지 않고, 어떤 단계에서 만들어졌는지 되돌아갈 수 있다. 목표는 설계 기준이며 기존 시스템 대비 시간 절감률은 아직 측정하지 않았다.

07. 핵심 흐름 B: 휴가·자원예약·회의

휴가: 내 근태→종류·기간·대체자 입력→해당 기간의 예상 잔여/정책 안내→제출→결재→연차 사용 원장과 달력 반영. 반려 시 예약분을 해제하고, 승인 후 취소는 취소 요청과 반대 기록을 남긴다.

차량: 일정에서 시간·차량 선택→일정 충돌 검증→승인 대기 점유→차량 신청서 제출→최종 승인 시 점유 재검증·확정→운행일지. 대기 점유 만료 시 재선택을 요구하고 자동으로 확정하지 않는다.

회의: 일정·참석자 입력→회의실 예약→회의록 작성→후속조치 업무 생성→필요하면 현재 버전 결재→확정본 열람. 회의록을 결재 양식에 다시 작성하는 경로를 없앤다.

모든 흐름은 원본 ID, 제출 버전, 관련 문서 링크, 실패 이유를 표시한다. 원래 화면으로 돌아갈 때 목록 위치와 필터를 유지한다.

08. 논리 아키텍처

선택: TypeScript 기반 Next.js 웹 UI + NestJS 업무 API + PostgreSQL + 비공개 객체 저장소 + 작업 프로세스. 초기에는 한 저장소와 한 업무 DB를 사용한다. API와 Worker는 같은 도메인 코드를 공유하지만 별도 프로세스로 배포한다.

NestJS의 모듈 경계를 활용해 도메인 간 공개 Application Service만 호출한다. 다른 모듈의 테이블에 직접 쓰는 코드는 금지한다. 공유 DB를 이용한 원자적 처리와 모듈별 테스트를 우선하고 마이크로서비스 분할은 독립 확장·장애 격리 필요가 측정된 뒤 판단한다. [T1]

Next.js는 UI·세션용 BFF를 담당하고 업무 규칙·최종 권한 검증은 API에 둔다. 상호작용 화면은 Client Component, 초기 화면 구성은 Server Component를 사용할 수 있다. 개인정보·테넌트 응답을 전역 공유 캐시에 저장하지 않는다. [T2]

10. 데이터 모델: 핵심 관계

모든 업무 테이블은 tenant_id를 갖는다. 참조는 (tenant_id, id)의 복합 외래키를 원칙으로 하여 다른 조직의 ID를 실수로 연결하지 못하게 한다. 사업자번호가 없는 상대방도 허용하며 식별번호는 검증·정규화 후 중복 후보로 사용한다. 같은 이름 또는 시설물 주소만으로 자동 병합하지 않는다.

JSONB는 사용자 정의 필드·결재 양식 스냅샷에 한정한다. 금액·기간·담당자·상태·참조키처럼 집계와 무결성이 필요한 값은 정규 컬럼으로 둔다. 모든 서비스의 데이터를 entity_type + JSON 하나에 넣지 않는다.

11-A. 운영 장부와 금액 처리 예시

매출 인식·청구·수금을 서로 다른 사건으로 저장한다. 내부 운영 보고를 위한 MVP이며 법정 재무제표·세액 계산·전자신고의 정확성을 보증하는 범위는 아니다. 공급가액·세액·총액과 인식일·청구일·입금일을 분리한다.

예시: 공급가액 100만원·세액 10만원의 청구에 입금 40만원을 충당하면 채권 잔여는 70만원이다. 이후 70만원을 충당하면 잔여 0원이 된다. 수익 인식 기준일의 운영 매출은 공급가액 100만원 한 번이고, 현금흐름에는 입금일별 40만원·70만원이 나타난다. 여기의 세액은 예시 입력값이다.

통장 내역이 들어오면 먼저 CashMovement 후보로 보관하고 기존 채권·채무와 연결한다. 이를 새 매출로 자동 생성하지 않는다. 파일 해시·행 키·계좌·제공자 거래 ID로 재업로드 후보를 탐지하되 같은 날짜·금액이라는 이유만으로 다른 실제 거래를 삭제하지 않는다.

선수금은 미충당 입금으로 유지하고, 수수료는 명시적 비용 항목으로 분리한다. 초과 입금·복수 청구 일괄 입금·부분 취소를 처리하며 삭제 대신 반대 충당·역기록을 남긴다. 보고서에는 거래/인식 기준과 현금 기준을 명시하고 기초잔액을 별도로 이관한다.

12. 승인 처리의 구현 순서

1. API가 actor의 테넌트·결재 권한과 Idempotency-Key를 검증한다. 2. ApprovalRequest와 현재 단계를 잠그고 expected_version, 제출 스냅샷, 활성 결재자를 확인한다. 3. 도메인 처리기가 휴가 잔여·자원 점유·근로 신청 조건을 재검증한다.

4. 최종 승인이면 도메인 원장/예약 상태와 결정 이력·감사·Outbox를 같은 PostgreSQL 트랜잭션에 저장한다. 5. 커밋 후 UI는 처리 결과와 관련 원본 링크를 받는다. 6. Worker가 알림·PDF·달력 읽기 캐시를 갱신한다.

다른 DB나 외부 제공자에 반영해야 하는 작업은 이 트랜잭션에 포함되지 않는다. 그 경우 “승인 완료 / 외부 처리 대기 / 실패”를 나누고 중복 방지와 재처리 이력을 제공한다. MVP의 휴가·예약은 같은 DB에 있어 이 복잡도를 피한다.

양식 13종을 지원하더라도 모든 양식에 자동 후속 처리를 붙이지 않는다. 휴가·차량·연장근로는 typed handler를 구현하고, 보고서·품의서·구매요청 등은 우선 승인 문서로 완료한다. 구매 승인만으로 지급이나 송금이 발생하지 않는다.

13. 권한·파일·검색 설계

인증은 OIDC Authorization Code + PKCE를 사용한다. 관리형 OIDC를 기본 선택으로 두고 자체 운영 요구가 확정되면 Keycloak을 대안으로 검토한다. 브라우저에 장기 토큰을 저장하지 않고 HttpOnly·Secure 세션 쿠키와 CSRF 방어를 적용한다. [T6]

권한은 역할(RBAC)에 조직·부서·공간·대상 레코드 범위를 더한다. owner/admin이라는 이유만으로 급여·신상 원문을 자동 열람시키지 않고 별도 HR/급여 권한으로 나눈다. 직원 디렉터리와 인사 원문 API 응답 모델을 분리한다.

PostgreSQL RLS는 테넌트 격리의 방어 계층으로 사용한다. 요청마다 트랜잭션 안에서 검증된 tenant context를 설정하고 연결 반환 시 상태가 남지 않도록 한다. 앱 계정은 테이블 소유자·superuser·BYPASSRLS 권한을 갖지 않는다. 레코드 및 필드 권한은 API에서 추가 검증한다. [T3]

14. API 계약과 공통 명령

REST + OpenAPI를 API 계약으로 삼고 프런트엔드 클라이언트를 생성한다. tenant_id는 요청 본문을 신뢰하지 않고 인증된 현재 조직에서 결정한다. 수정에는 version 또는 If-Match, 생성·승인·충당에는 Idempotency-Key를 적용한다.

일반 오류 형식은 {code, message, field_errors, retryable, correlation_id}로 통일한다. 인증 실패 401, 권한 거부 403, 상태/버전 충돌 409, 입력 오류 422를 구분하고 사용자에게 해결 행동을 제공한다.

15. 메일·채팅·외부 연동

메일 제공자는 아직 확인되지 않았다. 설계 예시는 Microsoft 365/Graph로 제시하되, 실제 파일럿이 Google Workspace 등 다른 제공자를 쓰면 1주차에 그 제공자 하나로 교체한다. 현재 사이트가 Microsoft 365를 쓴다는 뜻은 아니다.

메일 연결 어댑터는 authorize, syncFolders, syncChanges, readMessage, createDraft, send, move를 제공한다. 메시지·폴더 원본은 제공자에 있고 로컬에는 권한·연결·동기화 커서·필요한 메타데이터를 보관한다. Graph를 선택하면 폴더별 delta cursor와 제공자의 ID 특성을 반영한다. [T7]

발송은 outbox 명령으로 추적한다. 제공자 202는 접수이며 수신자 전달 성공을 뜻하지 않는다. 타임아웃 후 unknown 상태에서는 제공자/보낸편지함 확인 없이 무조건 재발송하지 않는다. 사용자에게 재확인 상태를 표시한다. [T8]

채팅은 WebSocket 전달 전에 DB 저장을 완료한다. 방별 순번과 client_message_id로 중복을 막고, 재접속은 마지막 seq 이후 메시지를 REST로 복구한다. 읽음은 사용자별 마지막 읽은 seq로 표현한다. 초기 API 1개 인스턴스에서는 별도 pub/sub 인프라 없이 시작할 수 있다.

전화 CTI·화상회의·AI 전사·은행 연동은 어댑터 경계만 정의하고 MVP에서는 수동 통화기록, 외부 회의 링크, CSV 가져오기를 제공한다. AI는 추후 추천 초안으로만 시작하고 승인·금액 확정을 직접 수행하게 하지 않는다.

16. 물리 배포와 운영 구성

처음에는 단일 리전에서 웹, 업무 API, Worker를 컨테이너로 운영한다. 데이터베이스·객체 저장소·비밀 관리·백업은 관리형 서비스를 우선 검토한다. AWS 서울 리전을 예시로 들면 ALB + 컨테이너 실행 환경 + RDS PostgreSQL + S3 + KMS/Secrets Manager로 매핑할 수 있으나 공급자·비용은 계약 전 검증 대상이다.

PostgreSQL Outbox를 Worker가 lease와 재시도 시각을 사용해 가져간다. 초기 Redis·Kafka·Elasticsearch는 필수 구성에서 제외한다. 실제 처리량·검색 품질·다중 API 인스턴스의 채팅 fan-out 요구가 생기면 각각 Queue/pub-sub/검색 서비스를 추가한다.

dev/staging/prod는 계정·DB·저장소·키를 분리한다. CI는 타입 검사·단위/통합 테스트·권한/상태 테스트→이미지 빌드·취약 의존성 검사→staging 데이터 이관 리허설→승인된 배포 순서로 구성한다. DB는 expand/contract 마이그레이션을 사용하고 파괴적 변경을 즉시 적용하지 않는다.

18. 이관 전략

기존 시스템의 DB나 공식 내보내기 접근은 아직 없다. 따라서 아래는 향후 이관 설계다. 스크린샷 데이터로 실제 운영 정보를 재구성하거나 무단 수집하지 않는다.

1. 공식 내보내기/DB 스키마를 받아 원본 ID·관계·상태·파일 참조를 조사한다. 2. staging import 테이블에 원본을 보존한다. 3. old_system + entity_type + old_id → new_id 매핑을 만든다. 4. 상대방·시설물·사용자·직원부터 적재한 뒤 계약·업무·결재·정산을 적재한다.

중복 후보는 사업자번호·연락처·주소·원본 관계로 제시하고 사용자가 확인한다. 병합하지 못한 레코드는 연결 관계를 유지한 채 남긴다. 결재 원본·확정 계약·장부는 임의 정규화로 내용을 바꾸지 않는다.

병행 검증 기간에는 기존 시스템을 원본으로 두고 새 시스템에서 쓰기를 제한한다. 전환 시 짧은 변경 동결→최종 차분→건수·금액·잔액·파일 해시 대조→원본 읽기 전용 보관으로 진행한다. 양쪽 자유 쓰기와 복잡한 양방향 동기화는 MVP에서 하지 않는다.

되돌리기는 데이터 백업만으로 끝나지 않는다. 전환 뒤 새 시스템에서 생긴 변경을 추출·대조하는 절차와 승인자를 정하고, 되돌릴 수 있는 시점/금액 기록의 보존 조건을 리허설한다.

19. 단계별 구현 계획

일정은 설계 추정이다. 전담 개발자 4명(프런트 2·백엔드 2), QA 1명, 디자이너/PM 각각 0.5명, 한 메일 제공자, 복잡한 세무·노무 자동화를 제외한 범위에서 18~22주를 예상한다. 현재 코드 재사용성·데이터 이관 난도가 확인되지 않아 확정 견적은 아니다.

모든 서비스의 핵심 흐름이 목표이므로 12주 중간 결과를 최종 MVP라고 부르지 않는다. P0/P1 분류는 서비스 삭제가 아니라 구현 순서와 출시 전 필수 조건을 정하는 기준이다.
