# CRUD 연관 데이터 점검 및 보완

점검·구현: 2026-09-25~26. JPA, 서비스·컨트롤러, 화면 및 운영 MariaDB `delidb`의 FK/집계 데이터를 비교했다. 운영 업무 데이터를 임의 생성하거나 과거 이력을 추측해 수정하지 않는다.

## 연계 정책

모든 연관 테이블을 cascade 삭제하지 않는다. 이미지·댓글은 종속 데이터이며 계약·계획·발주·입출고는 보존할 업무 기록이다. `ON UPDATE CASCADE`는 키 변경 규칙이지 이름·금액·상태 동기화가 아니다.

| 관계 | 등록·수정 | 삭제·취소 |
|---|---|---|
| 게시글 → 이미지·댓글 | 같은 DB 트랜잭션, 유지 이미지 UUID 보존 | 댓글 정리·flush 후 게시글 삭제, 이미지 행 cascade |
| 자재/제품 → 이미지 | 변경된 이미지만 추가/제거 | DB 참조가 막으면 전체 롤백; 파일은 커밋 후 큐 처리 |
| 제품계약 → 생산계획 → 조달계획 → 조달계약 → 발주 | 부모 관계 검증, 등록 시 스냅샷; 후속 업무가 있으면 상위 수정 제한 | 물리 삭제 대신 계약파기/계획중단/발주파기. 취소되지 않은 하위 업무가 있으면 상위 취소 제한 |
| 발주 → 검수 | 진행중/발주완료에서만 검수 내역 변경 | 발주 취소 시 검수 이력 유지; REMOVE cascade 제거 |
| 자재 → 재고 | 자재별 최대 1건, 입고 전 정확히 1건 필요 | 재고→자재 FK RESTRICT, 역방향 cascade 제거 |
| 발주 → 입고증빙 → 재고·입출고 이력 | 발주별 증빙 PK, 잠금과 단일 트랜잭션 | 증빙 기반 역분개, 원기록과 취소기록 모두 보존 |
| 기준정보 → 업무 기록 | FK와 이름 등 스냅샷 | FK RESTRICT로 참조 중인 기준정보 삭제 제한 |

## 추가 설계 항목 구현 결과

### 1. 입고 원자성·중복 방지·취소

`OrderWorkflowService.receive`가 발주 상태, 재고 수량/금액, `order_receipt`, `material_in_out_history`를 한 트랜잭션으로 처리한다. 요청 수량·단가·담당자 대신 DB 발주 수량, 계약 단가, 로그인 담당자를 사용한다. 화면의 선행 상태 변경 AJAX를 제거했다.

조달계획 → 발주 → 자재 → 재고 순서의 비관적 잠금을 사용한다. 같은 발주의 재전송은 추가 입고하지 않으며 다른 발주의 동일 자재 입고도 직렬화한다. 누계·증빙은 MariaDB REPEATABLE READ의 최신 커밋을 읽도록 잠금 조회한다.

입고 취소는 증빙 수량/금액으로 재고를 줄이고 `입고취소` 이력을 추가한다. 취소 이력 수량은 양수, 금액은 음수이며 구분값으로 방향을 판별한다. 증빙은 reversed, 발주는 발주파기로 남긴다. 재고·누적 입고량·금액이 부족하면 전체 취소를 거부한다. 취소 발주를 재사용하지 않고 새로 등록한다.

**기존 입고완료 발주 4건**은 과거 입고 이력과 확정 연결이 없었다. 재입고와 자동 역분개를 막고 소급 연결하지 않는다. 이 4건의 수동 데이터 보정은 별도 증빙 확인·승인이 필요하다.

### 2. 발주 완료와 조달계획 재계산

완료·검수 상태 변경·입고·취소 시 실제 발주가 속한 조달계획의 누계를 같은 트랜잭션에서 계산한다. 요청의 별도 계획 번호는 신뢰하지 않는다.

- 포함: 발주완료, 검수완료, 입고검수진행중, 반품진행중, 자재입고완료.
- 제외: 진행중, 발주파기.
- 요구 수량 이상이면 계획완료, 취소로 미달하면 진행중으로 복귀. 계획중단은 유지한다.
- 조달계획 수동 완료는 차단한다. 이는 **발주 확보량** 완료이지 실물 입고 완료가 아니다.

### 3. 순환 FK 및 재고 수동 관리

`databaseQuery/migrations/20260925_cascade_safety.sql`은 미사용 역방향 FK 3개를 제거하고 재고→자재를 DELETE/UPDATE RESTRICT로 바꾸며 자재별 재고 UNIQUE를 추가한다. 운영 조사에서 역방향 값은 전부 NULL, 자재/재고 각 1,323건, 중복 재고는 없었다.

역방향 값 또는 중복 재고가 있으면 DDL 전에 중단한다. 재실행 가능하며 복구 호환성을 위해 빈 역방향 컬럼은 유지한다. Hibernate update는 기존 FK 제거를 대신하지 못한다.

수동 재고 등록은 음수와 `누적 입고−누적 출고≠재고`를 거부한다. 최초 잔액 설정 용도이며 이력/입고증빙이 생긴 재고는 수정·삭제할 수 없다. 이력 없는 재고도 수량이 모두 0인 경우만 삭제한다.

### 4. 복제 필드 정책

자재명·코드·분류 변경은 재고와 BOM에, 제품명·코드·분류 변경은 BOM에 동기화한다. `Materials.change`의 자기 대입 오류도 수정했다. 재고 누적 금액을 현재 단가로 재평가하지 않는다.

계약·계획·발주의 복사 필드는 등록 시 DB 부모/기준정보에서 채우고 이후 기준정보 변경으로 덮어쓰지 않는다. 단가는 조달계획→조달계약 스냅샷을 따라 입고 금액에 사용한다. 상세/목록 DTO도 저장된 스냅샷을 우선 사용한다. 별도로 조인하는 연락처 등 현재 관계 정보와 운영상 부모 상태는 스냅샷 보장 대상이 아니다. 과거 누락·불일치 필드를 현재 값으로 일괄 덮어쓰지 않는다.

### 5. 커밋 후 물리 파일 삭제·재시도

이미지 DB 변경과 같은 트랜잭션에서 `file_deletion_task`를 적재한다. 30초 주기 작업이 커밋된 큐만 읽고 게시글·자재·제품 참조를 재확인한 후 원본/썸네일을 삭제한다. 실패는 큐에 남겨 최대 60분 간격으로 재시도한다. DB 변경 롤백 시 삭제 예약도 롤백된다.

클라이언트 삭제 파일 목록으로 즉시 삭제하지 않는다. 임시 업로드 삭제는 10분 유예하며 경로 탈출/심볼릭 링크를 거부한다. 유지 이미지 UUID와 밑줄 포함 파일명을 보존한다. 기존 업로드 폴더 전체를 일괄 청소하지 않는다.

### 6. 업무 이력 보존

계약·계획·발주 삭제 버튼은 업무 취소로 변경했다. 종료 업무 재활성화, 후속 업무가 있는 상위 수량 수정, 등록 API에 기존 ID를 보내 덮어쓰는 경로를 차단했다. 수정 화면으로 입고완료를 직접 지정할 수 없다. `COOPERATOR`, `PARTNER`는 향후 서비스용 예약 역할을 유지한다.

## 검증

Java 11에서 `bash gradlew cascadeTest bootJar --no-daemon` 성공. H2 회귀 테스트 16건: 게시글 삭제 1건, 역할 호환성 2건, 파일 삭제·롤백·재시도 5건, 입고/취소·롤백·동시성·누계·과거 데이터 보호·단가 스냅샷 8건. H2는 MariaDB 격리 수준 자체를 검증하는 것은 아니다.

운영 스키마만 복제한 별도 MariaDB에서 마이그레이션을 두 번 실행하고 역방향 FK 제거, RESTRICT, UNIQUE를 확인했다. 운영 업무 데이터에 CRUD 실험은 하지 않는다.

## 운영 반영·복구 절차

1. 기존 Docker 이미지를 별도 태그로 보존하고 새 이미지를 먼저 빌드한다.
2. 앱을 중단한 뒤 배포 폴더 밖에 권한을 제한한 전체 DB 덤프를 저장한다. 덤프 성공을 확인하기 전 DDL을 실행하지 않는다.
3. 마이그레이션을 적용하고 새 앱을 실행한다. 입고증빙·파일 큐 테이블과 이력의 nullable 발주/금액 컬럼은 현재 Hibernate update로 추가한다.
4. 컨테이너 재시작 횟수, 로그, HTTP 응답, FK 및 주요 행 수를 확인한다.
5. MariaDB DDL은 트랜잭션 롤백되지 않는다. 실패 시 앱을 중단하고 백업과 적용 단계에 맞춰 복구한다. 신규 업무 입력 후 과거 덤프를 무조건 복원하면 안 된다. 이전 앱 복귀도 신규 입고/역분개 내역을 먼저 검토한다.
