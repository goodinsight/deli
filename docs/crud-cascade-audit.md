# CRUD 연관 데이터 점검

점검일: 2026-09-25. 현재 Java 엔티티·서비스·컨트롤러·입고 화면과 운영 MariaDB `delidb`의 `information_schema.REFERENTIAL_CONSTRAINTS`를 읽어 비교했다. 운영 데이터의 생성·수정·삭제 실험은 수행하지 않았다.

## 결론

전체 업무 흐름이 자동 cascade로 연결되어 있지는 않다. JPA cascade는 소유한 하위 객체의 저장·삭제를 전파한다. DB의 `ON UPDATE CASCADE`는 참조 대상 키 변경을 반영하는 규칙이며, 자재명·단가·수량·업무 상태를 다른 테이블에 자동 복사하지 않는다. 후속 계약·계획 생성과 재고 계산은 별도 서비스 로직이 필요하다.

| 관계 | 생성·수정 | 삭제 및 운영 DB 규칙 |
|---|---|---|
| 게시글 → 이미지 | JPA ALL, orphanRemoval | JPA에서 이미지 정리, DB FK는 RESTRICT |
| 게시글 → 댓글 | 댓글 서비스에서 별도 저장 | 기존 댓글 정리 누락. 이번 수정으로 같은 트랜잭션에서 댓글 삭제·flush 후 게시글 삭제 |
| 자재/제품 → 이미지 | JPA ALL, orphanRemoval | JPA에서 이미지 정리, DB FK는 RESTRICT |
| 발주 → 검수 | JPA ALL, orphanRemoval; 검수 서비스도 별도 존재 | 검수는 JPA 연쇄 삭제. order_chart가 참조하면 DB RESTRICT로 발주 삭제 실패 가능 |
| 제품 → BOM·제품계약 | 참조를 지정해 개별 생성·수정 | RESTRICT. 제품 삭제로 계약·BOM이 자동 삭제되지 않음 |
| 제품계약 → 생산계획 → 조달계획 → 조달계약 → 발주 | 각 화면/서비스에서 개별 생성·수정 | 대부분 RESTRICT. 상위 변경이 후속 수량·상태·복제 필드에 자동 전파되지 않음 |
| 고객사/공급사/직원 → 업무 기록 | 참조와 일부 이름 필드를 저장 | 대부분 RESTRICT. 기준정보 삭제 시 업무 기록까지 지우는 방식은 부적절 |
| 자재 ↔ 재고 | 자재 등록이 재고 자동 생성을 보장하지 않음 | **양방향 DELETE CASCADE 존재**. 재고 삭제가 자재 삭제로 전파될 수 있음 |
| 재고 ↔ 입출고 이력 | 입고 컨트롤러에서 재고 갱신과 이력 등록 | 운영 DB 양쪽 FK는 RESTRICT. 이력이 있으면 재고 삭제 제한 |
| 업무 데이터 → 첨부 문서 | ManyToOne 참조, 자동 생성 없음 | RESTRICT. 공용 파일을 역방향 cascade로 삭제하면 안 됨 |

## 이번에 적용한 간단한 수정

1. `BoardServiceImpl.remove`: 댓글을 먼저 삭제·flush하고 게시글을 삭제한다. 기존 클래스 트랜잭션 안에서 수행하므로 게시글 삭제가 실패하면 댓글 삭제도 롤백된다. 게시글 이미지는 기존 JPA cascade로 삭제된다.
2. `MaterialProcurementPlanningServiceImpl`: 클래스에 트랜잭션을 적용해 조회·변경·저장 및 DTO 변환을 같은 영속성 범위에서 처리한다. 여러 컨트롤러 요청 전체를 하나의 트랜잭션으로 만드는 변경은 아니다.
3. `cascadeTest`: 운영 DB 대신 H2에서 댓글·이미지가 있는 게시글 삭제와 다른 게시글/댓글 보존을 검증한다. 기존 테스트는 DB 의존성이 있으므로 별도 Gradle 태스크를 추가했다. H2 검증은 MariaDB의 기존 수동 FK 구조를 재현하는 검증은 아니다.

## 추가 설계가 필요한 사항

- **입고의 원자성·중복 방지**: `readIncoming.html`은 상태 변경 AJAX와 입고 폼 제출을 별도로 실행한다. 컨트롤러는 재고 수정과 이력 등록을 각각 호출한다. 일부만 성공하거나 중복 입고가 가능하다. 서버에서 발주를 잠그고 DB의 수량을 읽어 상태·재고·이력을 한 트랜잭션으로 처리해야 한다. 다른 발주의 동일 자재 입고를 위한 재고 잠금과 취소 정책도 필요하다.
- **발주 완료 연계**: `OrderController.completeOrder`의 발주 상태 변경과 조달계획 완료는 하나의 트랜잭션이 아니다. 요청의 조달계획 번호 대신 DB의 실제 발주 관계를 검증하고 완료·취소 시 누적 수량 재계산 규칙을 정해야 한다.
- **운영 스키마의 순환 관계**: 자재↔재고, 재고↔이력, 생산계획↔조달계획에 역방향 참조가 있다. 일부는 현재 엔티티에 없는 과거 FK다. 데이터 사용 현황을 조사한 뒤 백업·마이그레이션으로 불필요한 관계를 제거하고 삭제 제한 정책을 통일해야 한다. `ddl-auto=update`만으로 기존 FK가 정리되지는 않는다.
- **복제 필드 갱신**: 자재명·제품코드·담당자명·단가 등의 복제 필드는 원본 수정으로 자동 갱신되지 않는다. 계약 당시 기록인지 최신 기준정보인지 구분한 후 동기화 범위를 정해야 한다.
- **물리 파일**: DB 이미지 행의 cascade와 `/upload`의 파일 삭제는 별개다. 파일 삭제는 DB 트랜잭션으로 롤백되지 않으므로 커밋 후 정리/재시도 구조가 필요하다.
- **업무 이력 보존**: 계약·발주·입출고 전체에 `CascadeType.ALL` 또는 `ON DELETE CASCADE`를 추가하면 이력이 소실될 수 있다. 진행된 업무는 삭제보다 취소·비활성화와 역분개가 적합하며 업무 규칙 합의가 필요하다.

이번 변경에는 운영 스키마 변경과 과거 데이터 보정이 포함되지 않는다.

## 검증 결과

Java 11에서 `bash gradlew cascadeTest bootJar --no-daemon` 성공. H2 회귀 테스트 1건 통과, 실행 JAR 빌드 성공. 테스트 컴파일을 막던 기존 조달계약 테스트의 빌더 메서드 대소문자 오타 2건도 수정했다. 이번 변경은 로컬에 적용했으며 운영 재배포는 수행하지 않았다.
